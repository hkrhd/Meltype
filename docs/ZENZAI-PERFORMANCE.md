# Mac の Zenzai small

## 設定

- 変換ライブラリは `d59a28e4c7ca049aef04f29a91eae9677a7753f2` のまま、`Zenzai` trait を有効化。`ZenzaiCPU` は使用しない。
- llama.cpp b4846 は配布バイナリでBF16カーネル初期化が失敗したため、同じ公開ABIのソースから `GGML_METAL=ON`・`GGML_METAL_USE_BF16=OFF` で再ビルドする。Q5_K_MモデルとF16 KV cacheを使用し、Metalを維持する。ソースのリビジョンとSHA-256は `mac/build-llama-metal.sh` で固定。ビルドにはCMakeも必要。Macの最低バージョンはランタイムに合わせ13.3。
- 公式 azooKey-Desktop が採用する `zenz-v3.1-small-gguf` の Q5_K_M（73,871,968 bytes）を利用。xsmall は使用しない。
- モデルの取得リビジョンと SHA-256 は `mac/fetch-zenzai-model.sh` で固定。重みは `mac/.build/models/` とアプリ内にだけ置き、リポジトリには含めない。
- `inferenceLimit: 2`、`requestRichCandidates: false`。1回では `でむこうかした → で向こう化した` が残ったため、最低限の品質を優先して上限2回とする。予測入力・個人最適化は有効にしない。
- 既存の64件までの変換結果キャッシュと、エンジンの増分計算・メモ化・KVキャッシュを利用。モデルはプロセス内で共有・mmap読み込み。
- 起動時に短い入力でウォームアップし、モデルロードとMetal初期化を最初のキー入力から切り離す。
- 今回は直前の文章との連携を追加しない。Core の既存処理が文脈あり・なしの両方を変換するため、連携するとキーごとのニューラル評価を重複させうる。

`inferenceLimit` は変換器1要求あたりのニューラル候補評価の上限であり、LLM内部のトークン計算全体が1ステップになるという意味ではない。Coreが1キーで複数の文節を更新する場合、変換器への要求も複数になりうる。

## 再計測

リポジトリ直下で実行する。

```sh
bash mac/build-cli.sh --test --build
bash mac/benchmark-conversion.sh
```

任意の読みの単発変換は、ビルドしたアプリに `--convert でむこうかした` を渡す。
`--convert` と `--benchmark-conversion` では `--inference-limit 1`（1〜5）を指定して上限を比較できる。通常のIME入力は上限2回で固定する。

`mac/.build/benchmarks/` に従来方式・ZenzaiそれぞれのJSONと標準エラーログを保存する。各条件は別プロセス、一時ディレクトリの設定・辞書・学習データを使う。普段の入力履歴は読み取らない。

- `converter`: 固定9文のかなを1文字ずつ増やし、実変換器の文節結果を取得。
- `keys`: ローマ字の各キーをNativeCoreへ渡し、ライブ変換の英日判定・候補更新を含む応答時間を測る。最後に確定した文字列も記録する。
- 5周分のp50/p95/p99・最大遅延と、初周の分布を別途記録。初期化は `startupWarmUpMs` として分離する。
- キャッシュは本番と同じ設定。固定文全体のprefix数は64を超えるが、エンジン内部のキャッシュも含めて利用される。
- `task_vm_info` のresidentとphysical footprintを初期化前後・各周後に記録。`time -l` のピークresident・footprintもログへ記録する。
- GUIのイベントループと同様に、キーごとの `autoreleasepool` で一時オブジェクトを解放し、解放時間もキー遅延に含める。
- IMKの描画・OSのイベント配送時間は含まない。モデル読み込みは新規プロセスで測るが、OSのファイルキャッシュは消さない。

## 実測

計測環境: Apple M2 Pro（10コア）、16 GB、macOS 27.2、Releaseビルド。

2026-10-17、固定9文×5周。モデル準備後の1149回のかな変換と2064回のキー処理を集計。p95は95%がその時間以内だったことを示す。

| 経路 | 方式 | 中央値 | p95 | 最大 | 終了時resident | 終了時physical footprint |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| かな変換単体 | 従来 | 2.19 ms | 6.55 ms | 33.47 ms | 96.2 MiB | 26.8 MiB |
| かな変換単体 | small・最大2回 | 8.70 ms | 14.19 ms | 47.10 ms | 174.2 MiB | 67.8 MiB |
| ライブ変換のキー処理全体 | 従来 | 3.37 ms | 30.03 ms | 214.35 ms | 148.6 MiB | 68.8 MiB |
| ライブ変換のキー処理全体 | small・最大2回 | 5.02 ms | 44.36 ms | 232.72 ms | 237.9 MiB | 122.6 MiB |

初周のキー処理p95は43.69 msで、周回キャッシュが温まる前も同程度。100 msを超えたキーはsmallで3/2064回、従来でも2/2064回あった。入力途中のローマ字が40文字以内の場合のp95はsmallで31.50 ms（従来17.04 ms）、40文字を超える部分は73.13 ms（従来52.05 ms）。短めの文章はライブ変換の実用域だが、長文の連続入力には遅延が残る。変換単体の測定には50 ms超はなかった。

ライブ変換のresidentは1周後236.8 MiB→5周後237.9 MiBで、繰り返しによる増加は約1.1 MiB。従来方式との差はresidentで約89 MiB、physical footprintで約54 MiBだった。`time -l` のピークresidentはsmallで238.7 MiB、従来149.5 MiB。

モデル準備は、OSのシェーダーキャッシュが温まった状態で122〜135 ms。BF16を外したランタイムを最初に動かした際のシェーダー生成込みでは約11.6秒だったため、初回導入時は起動に待ち時間がある。準備は最初のキー入力より前に行う。

実行ログで以下を確認した。

```text
load_tensors: offloaded 13/13 layers to GPU
ggml_metal_init: use bfloat = false
llama_kv_cache_init: Metal KV buffer size = 18.00 MiB
llama_init_from_model: Metal compute buffer size = 1.84 MiB
```

| このきのうはせっていがめんで… | この昨日は設定画面で… | この機能は設定画面で… |

最初の2例を実入力の回帰チェックへ追加。ユーザー辞書のlive on/offチェック、実入力48件、実エンジンでの1000回の入力・候補選択・確定・モード切替も確認した。

Core 446件、Swift 15件も成功。`mac/update.sh` のインストール後にmacOSが先にIMEを起動したため、起動スクリプトが自動起動済みサーバーも認識するよう修正。導入済みのプロセスがsmallモデルとMetalランタイムを読み込んでいること、および入力ソースの選択成功を確認した。

英日自動判定そのものは変更していない。固定コーパス中の一部の長文は従来方式・smallの両方で途中から英字扱いになった。かな変換単体では正しい文になるため、日本語エンジンとは別に残る課題である。今回の結果を、あらゆる長文で快適・常に正しいという保証にはしない。

## xsmall との比較（2026-10-18）

利用中のsmallアプリと、そのコピーのモデル重みだけをxsmallへ置き換えたアプリを比較した。コピーは再署名し、入力ソースとして登録・インストールしていない。通常利用はsmall・上限2回のまま。

xsmallは [Miwa-Keita/zenz-v3.1-xsmall-gguf](https://huggingface.co/Miwa-Keita/zenz-v3.1-xsmall-gguf) の `ggml-model-Q5_K_M.gguf`。リビジョン `5c0c4db8c8cc66a6ef01520475bebd56b41f6236`、SHA-256 `189638370c43292fd54ba5e83854b24887ddd57e8914e19095514e663f60c7f5` を検証した。重みは20,970,304 bytesで、smallの73,871,968 bytesから約72%小さい。モデルファイルの縮小率は、IME全体のメモリや遅延の縮小率とは異なる。

同じ9文×5周、各条件は独立プロセス、キー処理2064回を集計。辞書・学習データを分離し、履歴本文は使用していない。IMKの描画・OS配送は含まない。各条件1プロセスの測定なので、細かな差は実行順やOS状態の影響を含む。

| モデル・評価上限 | キー処理中央値 | p95 | p99 | 終了時resident | physical footprint |
| --- | ---: | ---: | ---: | ---: | ---: |
| small・2回（現設定） | 4.79 ms | 42.86 ms | 73.84 ms | 223.9 MiB | 123.7 MiB |
| xsmall・2回 | 4.29 ms | 34.98 ms | 63.75 ms | 180.7 MiB | 115.3 MiB |
| small・1回 | 4.79 ms | 40.84 ms | 68.62 ms | 241.7 MiB | 124.5 MiB |
| xsmall・1回 | 4.19 ms | 31.18 ms | 57.51 ms | 178.6 MiB | 112.2 MiB |

実際の `userdict.txt` だけを一時データへコピーした条件でも別途測定した（学習データはコピーしない）。small・2回は中央値4.59 ms / p95 41.77 ms / resident 240.1 MiB、xsmall・2回は4.23 ms / 31.70 ms / 177.9 MiB。xsmallでp95が約24%短縮し、residentは約62 MiB減った。physical footprintは122.9→111.3 MiBで、residentと同じ削減幅ではない。短い入力（40キー以下）のp95は30.33→19.58 ms、長い入力は66.09→58.04 ms。xsmallにしても長い入力や100 ms超のキー処理は残った。

品質面では、既存の実入力48例はsmall・2回で48/48、xsmall・2回で47/48だった。大半が英語または英日混在の回帰例であり、一般的な日本語精度の統計ではない。差が出た文は `きょうはにほんごのへんかんせいどをかくにんします` で、smallは「変換精度」、xsmallは「変換制度」。9文の計測でも同じ差が出た。また、上限1回では両モデルとも `でむこうかした` が「で向こう化した」へ悪化した。速度だけならxsmall・1回だが、この入力用途ではsmall・2回を維持する判断とした。

xsmallの初回プロセスはシェーダー準備込みで約2.8秒のウォームアップを要した。その後の条件との差を定常入力速度の比較に含めていない。結果JSONとログは `mac/.build/benchmarks/xsmall-evaluation-20261018/` に保存。smallとxsmallの各アプリへ `--benchmark-conversion --key-events --inference-limit 1` / `2` を渡して再計測できる。コピーのリソース名と既存JSON内のengine名はsmall表記のままなので、実モデルの識別には上記SHA-256と結果ファイル名を使う。

### 「もたつく燗事はある」の原因

smallの変換器単体は `もたつくかんじはある` を「もたつく感じはある」にする。Core経由でもユーザー辞書なしなら正しいが、`かん → 燗` を1件だけ登録するとsmall/xsmall両方で「もたつく燗事はある」を再現した。モデル変更で解決する問題ではない。

文節途中で辞書語を終わらせてよいかの判定が、変換結果の末尾に同じかなが残る場合をすべて許していた。「感じ」の送り仮名「じ」まで助詞と同じように切り離し、「かん」を「燗」、残りの「じ」を「事」へ再変換していた。文節内で切り離すかなは既存の助詞・助動詞表現で始まる場合に限定し、送り仮名を保護する。単独の「かん → 燗」と「燗をする」は維持する。

これは文字列と既存の語尾一覧に基づく判定で、完全な形態素境界判定ではない。今回の送り仮名への割り込みを止める修正であり、変換エンジン全般の誤変換をなくすものではない。
