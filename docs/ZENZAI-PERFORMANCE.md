# Mac の Zenzai small

Mac 版の変換に使う Zenzai の設定と、その根拠です。モデルを更新したらここも更新し、
推論上限1回と2回の精度を比べて、低下がなければ1回に減らします。

## 設定

- モデルは `zenz-v3.2-small-gguf` の Q5_K_M（73,871,936 bytes）。xsmall は使わない。
  リビジョンと SHA-256 は `mac/fetch-zenzai-model.sh` で固定し、重みはリポジトリに置かず
  `mac/.build/models/` とアプリ内にだけ入れる。
- 変換ライブラリは `d59a28e4` のまま `Zenzai` trait を有効化し、`ZenzaiCPU` は使わない。
- llama.cpp b4846 は配布バイナリで BF16 カーネルの初期化に失敗する。同じ公開 ABI のソースから
  `GGML_METAL=ON`・`GGML_METAL_USE_BF16=OFF` で再ビルドする（Q5_K_M、F16 KV cache）。
  リビジョンと SHA-256 は `mac/build-llama-metal.sh` で固定。CMake が要り、最低 macOS は 13.3。
- `inferenceLimit: 2`。1回では `でむこうかした → で向こう化した` が残る。`requestRichCandidates`
  は false で、予測入力・個人最適化は有効にしない。
- 変換結果のキャッシュ（64件）とエンジンの増分計算・メモ化・KV キャッシュを使い、モデルは
  プロセス内で共有して mmap で読む。起動時に短い入力でウォームアップする。
- 直前の文章との連携はしない。Core が文脈あり・なしの両方を変換するため、キーごとの
  ニューラル評価が重複しうる。

`inferenceLimit` は変換器1要求あたりのニューラル候補評価の上限で、LLM のトークン計算が
1ステップになる意味ではない。Core は1キーで複数の文節を更新するので要求も複数になりうる。

## 再計測

```sh
bash mac/build-cli.sh --test --build
bash mac/benchmark-conversion.sh
```

単発の変換は、ビルドしたアプリに `--convert でむこうかした` を渡す。`--convert` と
`--benchmark-conversion` は `--inference-limit 1`〜`5` で上限を変えて比べられる。結果の JSON と
標準エラーは `mac/.build/benchmarks/` に残る。

条件は全条件で共通。Apple M2 Pro（10コア）・16 GB・macOS 27.2・Release ビルドで、固定9文を
5周してキー処理2064回を集計する。条件ごとに別プロセス・一時ディレクトリの設定・辞書・
学習データを使い、普段の入力履歴は読まない。IMK の描画と OS のイベント配送は含めず、
`autoreleasepool` の解放は含める。各条件1プロセスなので、細かな差は実行順や OS の状態も含む。

## 結果

| キー処理（上限2回） | v3.1 (10-17) | v3.2 (10-19) |
| --- | ---: | ---: |
| 中央値 | 6.71 ms | 6.60 ms |
| p95 / p99 | 45.74 / 77.82 ms | 45.44 / 79.05 ms |
| 終了時 resident / footprint | 244.0 / 127.5 MiB | 242.4 / 127.5 MiB |

v3.1 と従来方式の比較（2026-10-17）:

| 経路 | 従来 | small・上限2回 |
| --- | ---: | ---: |
| かな変換単体の中央値 / p95 | 2.19 / 6.55 ms | 8.70 / 14.19 ms |
| キー処理全体の中央値 / p95 | 3.37 / 30.03 ms | 5.02 / 44.36 ms |
| 終了時 resident / footprint | 148.6 / 68.8 MiB | 237.9 / 122.6 MiB |

- 100 ms を超えたキーは 3/2064 回（従来 2/2064 回）。40文字以内の p95 は 31.50 ms（従来 17.04 ms）、
  それより長い部分は 73.13 ms（従来 52.05 ms）。短い文は実用域だが、長文を続けて打つと遅れが残る。
- 周回による resident の増加は約 1.1 MiB。5周目の `time -l` のピーク resident は 238.7 MiB
  （従来 149.5 MiB）。
- モデル準備はシェーダーキャッシュが温まっていれば 122〜135 ms。BF16 を外したランタイムの
  初回だけシェーダー生成込みで約 11.6 秒かかる。準備は最初のキー入力より前に済ませる。
- v3.2 は v3.1 と速度・メモリがほぼ同じで、9文中8文の結果も同じ。このコーパスでは精度向上は
  確認できていない。実入力・候補選択128件、Core 524件、Swift 32件、導入済みアプリでの
  入力・候補選択・確定・モード切替1000回は成功した。

### xsmall との比較（2026-10-18）

xsmall（`zenz-v3.1-xsmall`、20,970,304 bytes）は small・上限2回より p95 が約24%短く、
resident が約62 MiB少ない。ただし実入力48例は small 48/48・xsmall 47/48 で、
`きょうは…変換精度を…` が「変換制度」になった。上限1回では両方とも `でむこうかした` が
悪化する。速度だけなら xsmall・1回だが、small・上限2回を維持する。

## 品質

| 読み | 従来 | small・上限2回 |
| --- | --- | --- |
| でむこうかした | DEM高架下 | で無効化した |
| きょうはにほんごのへんかんせいどをかくにんします | 今日は日本語の返還制度を確認します | 今日は日本語の変換精度を確認します |
| このきのうはせっていがめんで… | この昨日は設定画面で… | この機能は設定画面で… |

最初の2例は実入力の回帰チェックに入れた。英日判定そのものは変えていない。固定コーパスの
長文の一部は従来方式でも small でも途中から英字扱いになる（かな変換単体では正しい）。

## 「もたつく燗事はある」の原因

変換器単体は正しい。`かん → 燗` を登録した状態で small・xsmall の両方が再現するので、
モデルの問題ではない。文節の途中で辞書語を終わらせてよいかの判定が「変換結果の末尾に同じかな
が残る場合」をすべて許していたため、送り仮名「じ」を助詞のように切り離し、「かん」を「燗」、
「じ」を「事」に再変換していた。切り離せるかなを既存の助詞・助動詞で始まる場合に限り、
送り仮名を保護する（単独の「かん → 燗」は維持）。文字列と語尾の一覧による判定なので、
変換エンジン全般の誤変換をなくすものではない。
